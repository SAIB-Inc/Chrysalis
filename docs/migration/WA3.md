# WA3: CIP-8 hashed payloads, span Base64Url, CLI key loading

CIP-8 signing and verification now honor the unprotected `"hashed"` header, bind addresses with the CIP-8 `"address"` label, enforce canonical unpadded ASCII Base64Url, and validate `Chrysalis.Wallet.Cli` key envelopes strictly.

- `CoseSign1Builder.WithAddress` now encodes the protected address header under the text-string label `"address"` (`HeaderLabels.Address`) instead of integer `-8`. Newly signed address-bound `COSE_Sign1` bytes change to match CIP-8, `cardano-signer`, Lucid, and Eternl; previously signed Chrysalis messages still verify because `EdDsaCoseSigner.VerifyCoseSign1` verifies `ProtectedHeaders` verbatim.
- `CoseMessageExtensions.GetSigStructure` and `EdDsaCoseSigner.VerifyCoseSign1` now read `"hashed"` directly from raw CBOR unprotected headers (definite and indefinite maps, skipping unrelated annotations): callers passing `payload` must supply raw plaintext (never a precomputed 28-byte digest), attached/caller payload mismatches throw `FormatException` (`VerifyCoseSign1` returns `false`), attached `"hashed": true` payloads with `payload: null` must be 28 bytes (never double-hashed), and malformed, non-boolean, or duplicated `"hashed"` entries are rejected. Passing `payload: null` authenticates only that `verificationKey` signed the attached bytes and protected headers verbatim (it cannot distinguish a raw 28-byte attachment from a digest or prove key-to-address ownership). Missing `"hashed"` defaults to `false`; `version` is neither emitted nor required.
- `CoseMessageExtensions.FromCip8Format` now enforces canonical unpadded ASCII Base64Url (`A-Z`, `a-z`, `0-9`, `-`, `_` with zero unused low bits in the final sextet) on payload and checksum before verifying the FNV-1a checksum, throwing `FormatException` for non-ASCII characters (was `NotSupportedException` on a non-ASCII unknown prefix with matching UTF-8 checksum), `+`, `/`, whitespace, `=`/`%` padding, `len % 4 == 1`, or non-zero trailing bits even when the checksum is stale; `InvalidOperationException` fires only for canonical unpadded Base64Url inputs whose checksum disagrees.
- `Chrysalis.Wallet.Cli` now reads 128-byte Shelley extended signing-key chain codes at offset 96 (was 64), rejects all 64-byte signing-key envelopes (such as `VrfSigningKey_PraosVRF`), validates typed envelopes against Ed25519 role and algorithm suffixes (`_ed25519` / `_ed25519_bip32`) while requiring exact 32- or 64-byte verification keys (preserving `cardano-signer` 32-byte public-only exports), and rejects trailing CBOR bytes or non-string/blank `"type"` properties (absent `"type"` remains accepted for 32/128-byte signing and 32/64-byte verification envelopes). `sign` removes the `Public Key (hex)` stdout line so raw `--vkey` bytes are never printed to terminal stdout (preventing accidental disclosure of an untyped signing key), renames key-length labels to `Decoded signing key length` / `Decoded public key length`, and fixes `sign --detached --hash-payload` self-verification. The CLI now catches `FormatException` (including `CborDecodeException`), so non-canonical signatures in `verify` and malformed hex in key files print `Error: ...` and exit 1 instead of crashing.
- `PublicKey.ToBlake2b224()` now delegates to `HashUtil.Blake2b224(Key)` and throws `ArgumentNullException` if `Key` is `null`.
- Clarification for WA2: for 32-byte seed keys, `PrivateKey.Derive` and `DeriveCardanoAccountKey` now throw `ArgumentOutOfRangeException` on a negative index (before WA2, seeds threw `InvalidOperationException`; 64-byte extended keys derived a hardened child).
