# Builtin bounds and decoding limits

From protocol version 11, `Evaluator.EvaluateScript` applies the node's argument bounds and decoding limits. Where the node takes a bounded integer argument (the integer arithmetic and comparison builtins, and `consByteString`'s byte under semantics variant D), a value outside −2^262143 to 2^262143 − 1 fails with `EvaluationException`; where it takes a bounded byte string argument, more than 65,536 bytes fails. Other positions and all results are not bounded. `writeBits` fails on more than 4,096 bytes, a BLS scalar multiplication on a scalar beyond 2^4095, a shift or rotation on an amount that does not fit in 64 bits, and `constrData` on a negative tag or one of 2^64 or more. A script with a constant whose type has more than 32 tags, or with a `constr` of more than 1,024 fields, is refused before it runs with `InvalidOperationException`. Below protocol version 11 these do not apply, as on the node.

At every protocol version, as on the node: `sliceByteString`, `indexByteString`, `readBit` and `indexArray` fail when an index or length does not fit in 64 bits, and `consByteString` (except where it wraps) and `replicateByte` when the byte is not 0 to 255, before the builtin is charged, so a script with a budget fails with `EvaluationException` rather than `BudgetExceededException`; `expModInteger` fails when an argument or the modulus lies beyond 2^8191, except that a modulus of 1 gives 0; a BLS multi-scalar multiplication checks every scalar, also those past the end of the shorter list; and `constrData`, `mapData`, `listData`, `writeBits` and the two BLS multi-scalar multiplications fail, before the builtin is charged, when a list argument's element type is not the one they take, even when the list is empty.

Reading is stricter on every path and at every protocol version, as the node reads. This applies wherever Flat or Plutus data bytes are read: `Evaluator.EvaluateScript` (the script, and arguments given as CBOR), `FlatDecoder.DecodeProgram`, `CborReader.DecodePlutusData`, `ScriptApplicator.ApplyParameter` and `ApplyParameters`, `ScriptExtension.ApplyParameters`, and the inline datums read by `ScriptContextBuilder.BuildTxInfoV3`, `BuildScriptContextV3`, `FindScript` and `EvaluateTx`, and so by `TransactionBuilder.Evaluate`. These throw `InvalidOperationException` for a constant type not in its canonical form, a variable index or `constr` tag that does not fit in 64 bits, and Plutus data that is empty or cut short, writes a byte string of more than 64 bytes in one piece (a bignum's included), writes a bignum tag in more than one byte, or has an item of the wrong kind. Tag 102 with an indefinite list is now read. `FlatDecoder.DecodeProgram` does not apply the 32-tag and 1,024-field limits.

Writing changes only for `constr` tags: `CborWriter.EncodePlutusData` and `EncodePlutusDataDefinite`, and through them `FlatEncoder.EncodeProgram`, `ScriptApplicator.ApplyParameter` and the `serialiseData` builtin, now write a tag of 2^63 or more, or a negative one, as the node does, instead of throwing or wrapping it. A negative tag, or one of 2^64 or more, is written as an integer, which neither the node nor Chrysalis reads back as a tag.

`Evaluator.EvaluateTerm` and `CekMachine` take a term that is already decoded, so only the builtin rules and `serialiseData`'s tags change there.

## Before

    byte[] parameter = HandWrittenCbor(); // a 65-byte byte string in one piece
    byte[] applied = ScriptApplicator.ApplyParameter(script, parameter); // was read; now InvalidOperationException

## After

    PlutusData value = new PlutusDataByteString(sixtyFiveBytes); // build the data from the original value
    byte[] parameter = CborWriter.EncodePlutusData(value); // writes pieces of at most 64 bytes, as the node requires
    byte[] applied = ScriptApplicator.ApplyParameter(script, parameter);
