# Plutus big integers over 64 bytes are written in chunks

`PlutusBigUint.Create` and `PlutusBigNint.Create` now write magnitudes longer than 64 bytes as indefinite byte strings of 64-byte chunks (`5f 58 40 ... ff`), matching the ledger's `bounded_bytes` rule. Built witness datums, redeemers, and inline datums carrying such integers now pass `decodeData`.

## Before

```csharp
PlutusBigUint.Create(magnitudeOf65Bytes); // Wrote c2 58 41 ... (one definite byte string, refused by the ledger).
```

## After

```csharp
PlutusBigUint.Create(magnitudeOf65Bytes); // Writes c2 5f 58 40 ... 41 ... ff (64-byte chunks, accepted by the ledger).
```

Witness datums, redeemers, and inline datums holding a magnitude over 64 bytes were already refused by `decodeData` in 1.x, so no transaction carrying those datum bytes on chain is affected. However, if you hashed `CborSerializer.Serialize(datum)` to set an output `datum_hash`, that hash (and any transaction rebuilt with it) changes in 2.0. An output locked by a Plutus script with the 1.x hash could not be spent because its matching datum was refused, whereas an output at a key or native-script address was accepted on chain and can be spent without supplying the datum; code that looks up or matches such an output by recomputing the hash in 2.0 gets the new value. Keep the original 1.x datum bytes or the hash read from the chain rather than recomputing it. Integers of 64 bytes or fewer, and values read from existing wire bytes, are unchanged.
