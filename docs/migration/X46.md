# Plutus data byte strings over 64 bytes are written in chunks

In your own `[CborConstr]` or `[PlutusData]` types, a `byte[]` or `ReadOnlyMemory<byte>` field longer than 64 bytes, or such a byte string in a list or map field, is now written in 64-byte chunks unless the field has `[CborSize]`. That is the form the ledger requires. 1.x wrote one byte string, which the ledger refuses in a datum or redeemer, so no transaction 1.x got onto the chain changes; only the datum hash of such a datum changes. Values read from CBOR keep their bytes when written back, and reading accepts both forms.

## Before

```csharp
[PlutusData(0)] public partial record MyDatum(long Amount, byte[] Owner) : CborRecord;
byte[] cbor = CborSerializer.Serialize(new MyDatum(1, ownerOf65Bytes)); // d8798201 5841 …: refused by the ledger
```

## After

```csharp
byte[] cbor = CborSerializer.Serialize(new MyDatum(1, ownerOf65Bytes)); // d8798201 5f 5840 … 41 … ff: accepted
```

Three kinds of byte string are still written in one piece, because the generator can't see them as Plutus data:
- inside another generic type, such as `Some<byte[]>` or `CborList<byte[]>`; the new warning CHCB004 names such a field;
- in a field whose type is a type parameter, such as `T` in `MyDatum<T>`;
- inside a `[CborList]` or `[CborMap]` type used in the datum.

Use `PlutusBoundedBytes` there, for example `Some<PlutusBoundedBytes>`, as generated blueprint types do.
