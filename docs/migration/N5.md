# Connection lifecycle, cancellation and reply time limits

## A silent node or peer now ends the connection

Both clients limit how long the other side may take to answer. When a limit
passes, the connection ends: the waiting call and every later call throw
`ConnectionClosedException`, and its `InnerException` is the new
`ReplyTimeoutException` (a `TimeoutException`; `Protocol` and `Limit` say which
reply and which limit). Dispose the client and connect again. Previously such a
call waited until its token was cancelled.

- `NodeClient`: the handshake reply has 10 seconds. Every reply of the local
  state query, local tx submission and local tx monitor protocols, and the reply
  to `ChainSync.FindIntersectionAsync`, has `NodeClient.ReplyTimeLimit`, 180
  seconds by default. After a `ChainSync.FindIntersectionAsync` that failed or
  was cancelled, that client's `ChainSync` refuses further calls with
  `InvalidOperationException`; dispose the client and connect again.
- `PeerClient`: the handshake reply has 10 seconds and each keep-alive reply 60
  seconds. A peer that goes silent is reported within the keep-alive interval
  plus 60 seconds, to every call waiting on that connection.
- A large local state query on mainnet (for example a whole-UTxO or
  stake-distribution query) can run longer than 180 seconds. Raise
  `ReplyTimeLimit` before the call, or set it to `Timeout.InfiniteTimeSpan` to
  turn the limit off; a new value applies to calls that start after it is set.
  The 10 and 60 second limits are fixed.
- Not limited: `ChainSync.NextRequestAsync`, which at the tip is answered when
  the next block arrives; `LocalTxMonitor.AcquireAsync` while a snapshot is
  held, which the node answers when the mempool changes; protocol objects built
  by hand from an `AgentChannel`.
- A call's own token still ends it with `OperationCanceledException`. A call
  cancelled after its request went out leaves its reply owed: discard the
  connection, as before.

Raise or turn off the limit before starting a long mainnet query:

```csharp
client.ReplyTimeLimit = TimeSpan.FromMinutes(10);
// Or turn the limit off:
client.ReplyTimeLimit = Timeout.InfiniteTimeSpan;
```

## `StartAsync` takes a token

`NodeClient.StartAsync(ulong networkMagic = 2, CancellationToken cancellationToken = default)`
and `PeerClient.StartAsync(ulong networkMagic = 2, TimeSpan? keepAliveInterval = null, CancellationToken cancellationToken = default)`.
Existing calls compile unchanged; rebuild. The token cancels start-up only. A
`PeerClient` start that fails, or is cancelled after it has begun, now disposes
the connection, as `NodeClient`'s already did, and a second `StartAsync` on the
same `PeerClient` throws `InvalidOperationException`.
`PeerClient.NegotiatedVersion` gives the accepted version.

## `DisposeAsync`

Both clients implement `IAsyncDisposable`. `await using`, or
`await client.DisposeAsync()`, returns once the read loop and the keep-alive loop
have stopped and the socket is closed. `Dispose()` is unchanged and returns
earlier. The analyzer rule CA1849 now asks for `await client.DisposeAsync()`
where an async method calls `client.Dispose()`. `PeerClient.Dispose()` may be
called more than once.

## Two cancellation fixes

- `ChainSync.NextRequestAsync`, called after a wait that was cancelled or failed,
  reads the reply that is still owed, or throws the connection's error. It
  returned null before.
- A send cancelled after the first segment of a message larger than one segment
  (65,535 payload bytes) still throws `OperationCanceledException`, and now also
  ends the connection: later calls throw `ConnectionClosedException` with an
  `IOException` inside.
